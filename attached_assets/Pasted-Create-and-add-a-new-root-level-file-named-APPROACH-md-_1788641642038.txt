# Approach

## 1. Problem Understanding

Explain the core problem:
An AI tutor can provide a technically correct explanation, but the student may simply read it and leave without actually understanding or remembering the concept.

Explain the product problem as:
The missing step is an active learning interaction between "AI explains" and "student leaves".

Make the distinction between:
- receiving information
- demonstrating understanding

Do not claim that every student fails this way; describe it as the key failure mode the product is designed to address.

## 2. User

Define the primary user as:
A student who uses an AI tutor to understand a concept or solve a learning question.

Describe the user's goal:
- Understand the concept
- Check whether they actually understood it
- Continue learning without unnecessary friction

Describe the user's likely frustration:
They may feel that an explanation makes sense while reading it, but may not be able to explain the idea themselves.

## 3. Assumptions

List the main assumptions behind the solution, including:
- The student has already asked a learning question.
- The AI explanation is the starting point for learning, not the end point.
- A short active-recall interaction is more useful than immediately showing another long explanation.
- Students need feedback when their understanding is incomplete.
- A low-friction interaction is more suitable for a small learning session than a large dashboard or course system.
- AI can be mocked for the prototype because the assignment evaluates the learning interaction and engineering design rather than model quality.

## 4. Proposed Solution

Explain the product concept "CogniBloom – Active Learning Tutor".

Describe the core interaction:

Student question
→ AI explanation
→ "Let's check your understanding"
→ Student explains the concept in their own words
→ System evaluates the response
→ Targeted feedback
→ Retry if needed
→ Completion

Explain why "Explain it yourself" was selected:
- It requires active recall.
- It reveals whether the student can reconstruct the concept rather than recognize it.
- It creates a natural opportunity for feedback.
- It is simple enough to complete in one short session.
- It directly addresses the assignment's problem of passive consumption.

Explain that the prototype uses deterministic mocked evaluation so the complete experience can be demonstrated reliably.

## 5. User Flow

Describe the actual implemented flow step-by-step:

1. Start Learning
   - Student enters/selects a topic/question.
   - Empty input is validated.

2. Explanation
   - The system generates/displays an explanation.
   - The student is explicitly encouraged to check their understanding instead of simply leaving.

3. Concept Check
   - Student is asked to explain the concept in their own words.
   - Student can submit an answer or skip.

4. Evaluation / Feedback
   - The backend evaluates the response.
   - The result can be correct, partially correct, or incorrect.
   - The UI gives feedback appropriate to the result.

5. Retry
   - Incorrect or partial responses can be retried.
   - Attempt numbers are tracked.

6. Completion
   - A successful interaction can lead to the completed state.
   - Skipping is clearly treated differently from successfully demonstrating understanding.

7. Restoration
   - The frontend stores the active session locally and can restore the learning state after refresh.

## 6. Product Decisions

Explain the important decisions:

### Chosen: Explain-it-yourself concept check
Why:
- Directly addresses the problem.
- Small cognitive effort.
- Produces meaningful evidence of understanding.
- Easy to complete and evaluate.

### Feedback + Retry
Why:
- A wrong answer should not be a dead end.
- Feedback turns failure into another learning opportunity.
- Retry supports learning rather than simply scoring the student.

### Low-friction single-session experience
Why:
- The assignment asks for a small learning interaction.
- A dashboard, account system, course catalogue, streak system, etc. would distract from the core problem.

### Local session restoration
Why:
- Students may refresh or temporarily leave.
- Restoring the active session reduces frustration and supports continuity.

## 7. Rejected / Deferred Alternatives

Discuss alternatives that were considered but not implemented in this prototype:

### Multiple-choice quiz
Rejected as the primary interaction because recognizing the correct option can be easier than generating an explanation independently.

### Large quiz system
Deferred because it increases scope without directly improving the core learning interaction.

### Confidence rating as the main interaction
Deferred because confidence is useful metadata, but it does not itself demonstrate understanding.

### Full adaptive difficulty engine
Deferred because the prototype first needs to prove the core interaction loop.

### Authentication / student dashboard
Deferred because this is a single-session learning prototype and authentication does not solve the central learning problem.

### Real external AI integration
Deferred in the prototype so the learning flow remains deterministic, testable, and reliable.

## 11. Edge Cases Considered

Document the actual handling:

- Empty question/input → validation prevents submission.
- Student gives an incorrect answer → feedback + retry.
- Student gives a partially correct answer → targeted feedback / retry path.
- Student skips → separate skipped state; skipping is not presented as successful learning.
- Interaction API failure → friendly error and retry.
- Backend unavailable → clear error state.
- Page refresh → active session can be restored locally.
- Student leaves midway → local restoration helps preserve the active session.
- Repeated difficulty → retry remains available and the feedback can guide another attempt.
- AI unavailable → prototype uses deterministic mocked learning behavior rather than depending on an external AI service.

Be careful not to claim that repeated-failure escalation is a sophisticated adaptive engine; it is not.

## 12. Trade-offs

Explain these honestly:

### Mocked AI instead of real AI
Trade-off:
Less realism, but deterministic behavior makes the prototype reliable and keeps the focus on the product interaction.

### One core interaction type
Trade-off:
Less variety, but clearer validation of the central hypothesis.

### No authentication
Trade-off:
No multi-user account system, but much lower complexity for a single-session assignment prototype.

### SQLite
Trade-off:
Simple and fast for a small prototype, rather than introducing the operational complexity of a hosted production database.

### No analytics dashboard
Trade-off:
Metrics are defined conceptually but not instrumented because the assignment does not require analytics implementation.

### Feedback endpoint not persisted
Be transparent:
The endpoint validates and accepts feedback, but the current data model does not persist it. This keeps the current schema focused on the learning session and interaction loop.
